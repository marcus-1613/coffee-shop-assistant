# 技术方案设计（ADR — 架构决策记录）

> 企业级项目习惯：每个关键技术选型都记录"为什么这么选、放弃了什么"。
> 这是面试官判断你"会不会做架构"的重要依据。

---

## ADR-001：Web 框架选 FastAPI

**背景**：Java 项目用 Spring Boot，Python 侧需要等价物。

**决策**：选 FastAPI。

**理由**：
- 原生支持 async/await，与 Agent 的异步流式天然契合
- 自动生成 OpenAPI 文档（`/docs`），调试方便
- 基于 pydantic 做请求/响应校验，与我们的数据模型统一

**放弃的选项**：
- Django：太重，不适合纯 API 服务
- Flask：异步支持弱，需额外扩展

---

## ADR-002：Agent 状态机用 LangGraph（而非手写 if/else）

**背景**：Java 项目用 613 行 if/switch 手写状态机（虽声明了 LangGraph4j 依赖但没用）。

**决策**：用 LangGraph 的 `StateGraph` + `checkpointer` 实现状态机。

**理由**：
- 图 + 条件边表达状态流转，比 if/else 清晰一个数量级
- `checkpointer` 原生支持状态持久化，多轮会话恢复、断线重连"白送"
- 这是 Java 项目最大的短板，正好是"超越"的抓手

**放弃的选项**：
- 手写状态机照搬 Java：Python 这么写是"倒退"，浪费 LangGraph 的优势

---

## ADR-003：数据库先用 SQLite，预留 PostgreSQL

**背景**：Text2SQL 需要数据源；Java 项目用 PostgreSQL + MySQL 双主从。

**决策**：MVP 用 SQLite + 演示数据，架构层抽象出"数据源接口"，预留 PostgreSQL。

**理由**：
- SQLite 零配置，立刻能跑，不依赖外部环境
- 通过 SQLAlchemy 抽象，切换 PostgreSQL 只需改连接串 + 驱动

**放弃的选项**：
- 一开始就上 PostgreSQL：新手要先装环境、配连接，拖慢学习进度

---

## ADR-004：大模型用 DeepSeek，抽象 Provider 可切换

**背景**：Java 项目用智谱 GLM。

**决策**：默认 DeepSeek（OpenAI 兼容接口），抽象 `LLMProvider` 接口，可切 GLM/其他。

**理由**：
- DeepSeek 便宜、SmartCommute 项目验证过
- 用 LangChain 的 `ChatOpenAI` 统一接口，换模型只改 base_url + key

---

## ADR-005：SQL 安全校验用 sqlglot（AST 级）

**背景**：Java 项目用 JSQLParser 手写规则校验。

**决策**：用 sqlglot 做 AST 级 SQL 解析与校验。

**理由**：
- 解析成 AST 后做结构化检查（如：只允许 SELECT、禁止多语句、禁止危险函数），比字符串匹配可靠
- sqlglot 是 Python 生态最成熟的 SQL 解析库

---

## ADR-006：LLM 决策与确定性逻辑分离

**背景**：SmartCommute 项目的核心教训——不要让 LLM 做本可确定性完成的事。

**决策**：
- 确定性逻辑（状态流转、SQL 安全校验、事件审计）用纯 Python 实现，可单测
- LLM 只负责"生成 SQL""判断意图""反思"等真正需要智能的部分

**理由**：可测试性 + 可靠性，这是"超越"Java 项目的工程质量核心。

## ADR-007：前端选 React（而非 Vue）

**背景**：Java 项目前端是 Vue 3。

**决策**：选 React。

**理由**：
- SmartCommute 项目已用 React 验证，能复用其经验和工程习惯
- React 生态在前端 Agent 交互场景更丰富

**放弃的选项**：
- Vue 3：与 Java 项目一致，但会重复 SmartCommute 已走过的路

## ADR-008：Agent 循环必须设置最大重试上限（防死循环）

**背景**：AI 生成的 SQL 可能反复出错（语法错误、字段名写错等）。如果失败后无限制地让模型反思重试，会陷入死循环，无限消耗 Token/费用，甚至导致服务卡死。

**决策**：Text2SQL 引擎设置 `MAX_RETRIES = 3`。执行失败后把错误信息喂回模型让其反思重写；重试耗尽后停止循环，返回友好的错误提示，而不是继续重试或抛出异常。

**理由**：
- 这是所有 AI Agent 的「策略限制」铁律——任何循环都必须有上限（最大步数/时长/重试次数）
- 防止不可控的资源消耗和糟糕的用户体验

**放弃的选项**：
- 无限重试：会导致死循环，不可接受
- 失败即抛异常：体验差，且浪费了 LLM「自我纠错」的能力

## ADR-009：引入意图路由（Intent Router），失败成本前置

**背景**：早期版本不管用户问什么（包括"你好"、"今天天气怎么样"），都硬跑 Text2SQL 链路——生成 SQL → 执行 → 失败 → 自我纠错，一直打到 `max_retries=3` 才停。导致：无关问题白白烧 3 次大模型调用，用户干等，体验差。

**决策**：在 Agent 图最前面加「意图分类器」，把输入分为：
- `chat`（闲聊/无关）→ 直接走 LLM 通用对话，不碰 Text2SQL
- `analysis`（数据查询/分析）→ 走数据源查询 + 出图 + 汇总

**关键澄清**：这不是"拦掉无关问题、回一句死话"，而是"分流"——闲聊也走大模型，只是走「通用对话」链路而非「Text2SQL」链路。

**理由**：
- 「失败成本前置」：在开始干活前先判断"这活该不该接、走哪条路"，避免无谓消耗
- 这是 Agent 工程的标准做法（JD 里反复出现的"意图识别 + 任务分流"）

**放弃的选项**：
- 一刀切拦掉闲聊、返回固定文案：体验差，且浪费 LLM 的通用对话能力

## ADR-010：数据源抽象接口 + 注册表（支持多源热插拔）

**背景**：早期版本数据绑定死一个 SQLite 医院库。换数据源要重写 Text2SQL、Schema 提示、仓储层，是"玩具项目"和"企业项目"的分水岭。同时，真实外部数据源（如公开 API）是"不可控"的——会停更、改版、限流、下架。

**决策**：
1. 定义 `DataSource` 抽象接口（name / description / schema / query 四个方法）
2. `DataSourceRegistry` 注册表管理所有数据源，Agent 启动时自动发现
3. 首个实现 `DiseaseShSource`（对接公开健康数据 API）
4. 数据源查询结果统一携带 `meta.chart`（图表建议）+ `meta.latest_date`（数据新鲜度）

**理由**：
- 加一个数据源 = 写一个类 + 注册一下，核心代码零改动（换源不动核心）
- 「数据新鲜度」是数据诚实——数据源停更时要主动告知，而不是假装实时
- 缓存（TTLCache）解决第三方限流、降低延迟

**放弃的选项**：
- 硬编码多个 if-else 处理不同数据源：堆料、不可维护，面试官一眼看穿

**备注（真实的坑）**：Disease.sh 的疫情数据已于 2023 年 3 月停更。这恰好验证了"数据源不可控"这个判断——也验证了抽象接口的价值（可换源）。

## ADR-011：用户认证（JWT）+ 资源隔离（owner 校验）

**背景**：此前系统没有任何用户概念——所有请求一视同仁，聊天记录不归属任何人。这会导致两个致命安全问题：
1. 任何人都能调用接口，没有身份识别
2. 即使加了登录，若查询数据时不校验归属，用户 B 就能通过手动改 ID 读到用户 A 的隐私数据（越权漏洞 / IDOR）

**决策**：
1. 认证：`User` 表 + bcrypt 密码哈希 + JWT 令牌（`python-jose` 签发/校验）
2. 资源隔离：`Conversation` 表每条记录绑定 `user_id`，查询时**强制校验 `owner == 当前用户`**，否则 403
3. 身份注入：`get_current_user` 依赖（FastAPI Depends），从请求头解析 token → 查用户 → 注入接口

**理由**：
- 认证（你是谁）和授权（你能碰什么）是**两层独立的安全**，缺一不可
- JWT 是无状态认证：服务端不存 session，靠签名校验真伪，水平扩展友好
- 密码绝不存明文（bcrypt 哈希），数据库泄露也不至于直接暴露密码
- owner 校验必须在服务端做，**绝不能相信前端传来的资源 ID**——这是防越权的铁律

**放弃的选项**：
- Session 认证（服务端存 session）：有状态，不利于分布式扩展
- 只加登录不做资源隔离：等于没加，越权漏洞依然存在
- 密码存明文：绝对禁止，属于 P0 级安全事故

**备注（真实的坑）**：`passlib` 库已停止维护，与 `bcrypt 5.x` 不兼容（哈希时抛 `ValueError: password cannot be longer than 72 bytes`）。最终**放弃 passlib，直接用 `bcrypt` 库**——这是"依赖选型要看维护状态"的实战教训。

## ADR-012：消息持久化（后端是聊天记录的唯一可信写入方）

**背景**：此前聊天是"流式输出到前端就完事"，服务端不落库。用户刷新页面历史就丢，且后端无法追溯"谁在何时问了什么"——既缺审计，也缺故障排查依据。参考文档明确要求："后端统一持久化消息，断连保存 partial"。

**决策**：
1. 新增 `MessageRepository` 持久化服务，采用**两段式写入**：
   - `create()`：进入时先存「用户提问」，answer 暂空（断连也保留 partial）
   - `complete()`：AI 回答生成后，更新 answer 回那条记录
2. 「可选登录」语义：登录用户（有 token）的消息绑定 `user_id` 落库；匿名用户不落库
3. 复用上一阶段建的 `Conversation` 表，不再新增表

**理由**：
- 后端是聊天记录的「唯一可信写入方」——前端只是展示，不是权威
- 两段式写入对应「断连保存 partial」：即使 SSE 流中断，question 也已在库
- 落库的消息可审计（谁问了什么）、可排查（出了 bug 能翻历史定位）

**放弃的选项**：
- 只在结束时一次性落库：断连则全丢，不满足 partial 要求
- 强制登录才能聊天：会让这一步耦合"前端登录页"，扩大范围

**关联**：与 ADR-011（用户认证）配合——持久化需要知道"消息属于谁"，正好用 `get_current_user`（可选版）提供身份。

## ADR-013：多轮记忆（滑动窗口 + 按用户隔离）

**背景**：此前每次请求都是"孤立"的——大模型本身无状态，不喂历史就不知道上一句聊了什么。用户问"美国疫情"，接着问"那日本呢"，系统无法理解"那"的指代。这是 Agent 从"单轮"走向"多轮对话"的关键。

**决策**：采用**滑动窗口**策略做多轮记忆：
1. `MessageRepository.get_recent_history(user_id, limit=5)` 捞取最近 5 轮对话
2. 喂给 LLM 前，拼成「历史对话」文本段（用户：… / 助手：…）
3. **按 user_id 隔离**：只捞当前用户自己的历史（呼应 ADR-011 资源隔离）
4. **只取有回答的完整轮次**：跳过 answer 为 None 的 partial 记录

**理由**：
- 记忆的本质不是"让模型记住"，而是"程序把历史捞出来、拼进去、一起喂"
- 滑动窗口是"记忆取舍"的最简正确解：避免上下文超长、token 成本失控、旧消息噪声干扰
- 按用户隔离是安全底线——用户 A 的历史绝不能喂给用户 B

**放弃的选项**：
- 无脑全量塞入：超出上下文窗口、烧钱、噪声干扰
- 摘要压缩：中级方案，但引入"摘要 LLM 调用"，复杂度高，本阶段不做
- 向量检索（RAG 式记忆）：最强但最重，需 embedding + 向量库，留待后续 RAG 阶段

**关联**：复用 ADR-012 的 `Conversation` 表作为记忆存储；依赖 ADR-011 的 `get_current_user` 提供身份来隔离。

## ADR-014：工具抽象层（Tool + ToolRegistry + ToolPlanner）

**背景**：此前数据链路是「手写流水线」——意图 → 动作规划 → 查 Disease.sh → 汇总，写死在 `chat.py` 里。只有「一个数据源」+「一条固定链路」。一旦要加第二个工具（计算器、查天气、第二个数据源），就得改主流程。这违背「开闭原则」，也让 Agent 无法真正「多工具协作」。

**决策**：引入「工具（Tool）」这一层抽象，让 Agent 面对「统一的能力集合」：
1. `Tool` 接口：每个工具有 `name` / `description` / `parameters` / `run(**params)`，向大模型「自我介绍」
2. `ToolRegistry`：把工具收集起来，生成「工具清单」喂给 LLM，让模型「选工具」而非代码 if-else 硬编码
3. 两个具体工具：`DataSourceTool`（包装数据源执行器）、`AnswerTool`（包装 LLM 直答），统一成相同调用协议
4. `ToolPlanner`：输入 = 问题 + 工具清单，输出 = 结构化工具调用（`{"tool": ..., "params": {...}}`），是 `DataSourceActionPlanner` 的通用化

**理由**：
- 依赖倒置：上层 Agent 只依赖 `Tool` 接口，与 `LLMProvider` / `DataSource` 一脉相承
- 可扩展：加工具 = 写一个类 + 注册一行，核心流程零改动（开闭原则）
- 业界标准：对齐 OpenAI function calling / LangChain tool 的「模型选工具」范式，面试可讲

**放弃的选项**：
- 继续在 `chat.py` 里写死 if-else 分流：加工具必改主流程，不可扩展
- 直接依赖 LLM 原生 function calling 输出：可控性、可测试性弱，且 DeepSeek 的 function calling 生态需额外适配

**关联**：`DataSourceTool` 内部复用 ADR-010 的 `DataSourceExecutor`；为下一阶段「状态机 executor 改为选工具执行 + REPLAN」打基础。

## ADR-015：重写 Agent 状态机为「多工具 + REPLAN」循环

**背景**：旧状态机（`planner → executor → reflector → summarizer`）是给 Text2SQL 设计的——executor 写死调 `Text2SqlEngine`，reflector 只是「重置状态重试同一步」（真正的纠错在引擎内部 max_retries），无法「多工具协作」，也无法「失败后换思路」。

**决策**：重写 `state.py` / `nodes.py` / `graph.py`，让状态机围绕「工具调用序列」运转：
1. **planner**：用 ADR-014 的 `ToolPlanner` 把问题翻译成「工具调用序列」
2. **executor**：从 `ToolRegistry` 按名字选工具、执行（不再写死 Text2SQL）
3. **reflector（REPLAN）**：失败时让 LLM 反思失败原因，**重新生成计划**（换工具 / 调参数 / 拆步骤），而非原地重试
4. **answer**：汇总结果（复用 `AnswerTool`，保持「一切皆工具」）
5. **clarify**：信息不足时反问用户（从 chat.py 收编进状态机）
6. **decision** 新增 `replan` / `clarify` 路由；`replan_count` 上限 MAX_REPLAN=3 防死循环

**理由**：
- REPLAN 是「失败成本控制」的升级版：旧 max_retries 是「同一 SQL 重试」，REPLAN 是「反思后换方案」，真正体现 Agent 的「自我修正」
- 多工具协作：executor 面对的是「工具」这一统一概念，加工具不改状态机
- 澄清追问收编进状态机，让「反问用户」成为图的一部分（而非散在 chat.py）

**放弃的选项**：
- 旧文件小修小补：结构会越来越僵，且旧状态机围绕 Text2SQL 的语义已不适用
- 新建 v2 并行：会产生两套状态机，需后续清理，边界不干净

**关联**：依赖 ADR-014（工具抽象）+ ADR-010（数据源）+ ADR-013（澄清追问逻辑复用）。旧 `planner.py`（`Planner` 类）成为死代码，待后续清理。

## ADR-016：API 层与引擎层解耦（意图路由在入口，状态机在引擎）

**背景**：此前 `chat.py` 里手写了一条「意图 → 动作规划 → 查 Disease.sh → 汇总」的完整流水线，既管「路由」又管「执行」，职责混杂。2-B 重写了状态机后，需要决定「意图判断」到底放哪层。

**决策**：分层解耦——
1. **API 层（chat.py）**：负责「意图路由」（IntentClassifier 判断 chat/analysis）+ SSE 流式输出 + 多轮记忆 + 消息持久化
2. **引擎层（app/agent 状态机）**：负责「怎么干」（planner 选工具 → executor 执行 → reflector REPLAN → answer 汇总）
3. 数据分析请求 → 用 `graph.stream(stream_mode="updates")` 驱动状态机，每走完一个节点向 SSE 发一个事件（intent/planner/executor/summary/chart/done），前端实时看到进度

**理由**：
- 意图判断的结果决定「要不要启动状态机」——闲聊根本用不上重武器，判断必须站在状态机前面（「路由在入口」）
- 两层各自可独立替换：换意图分类策略只改 API 层；换状态机框架只改引擎层（开闭原则）
- 失败责任边界清晰：意图判断失败 → 兜底继续；状态机某步失败 → REPLAN 反思重规划
- LangGraph `stream_mode="updates"` 天然把「每走完一个节点」暴露成流式事件，与 SSE 完美契合

**放弃的选项**：
- 把意图判断塞进状态机当第一个节点：闲聊也得先跑进状态机绕一圈，回到「闲聊也烧 API」的老路
- 状态机跑完一次性返回（不用 stream）：前端失去实时进度反馈，体验倒退

**关联**：依赖 ADR-015（多工具状态机）+ ADR-013（多轮记忆）+ ADR-012（消息持久化）+ ADR-011（认证）。

## ADR-017：产品定位转向「咖啡店经营助手」+ 复活 Text2SQL 为第二工具

**背景**：项目原定位是「疫情数据分析助手」（单一数据源 Disease.sh）。用户质疑"多数据源助手"抽象且不接地气，提出转向更聚焦、有真实业务画面的方向。

**决策**：
1. **定位**：从「通用/疫情数据分析助手」改为「**咖啡店经营助手**」——店长的数据副手，核心能力是「结合天气预报 + 历史销量，辅助分析备货」。
2. **本地知识库**：新增 4 张咖啡店经营表（`cafe_members` 会员 / `cafe_products` 饮品 / `cafe_orders` 订单 / `cafe_order_items` 明细），其中 `products.cost` 支撑"毛利分析"，`orders.weather` 支撑"天气×销量关联"。
3. **复活 Text2SQL**：把闲置的 `Text2SqlEngine` 包装成 `SqliteTool`（第二数据工具），与 `DataSourceTool` 并列注册进 ToolRegistry，planner 按问题语义自动分流（经营问题→本地库，疫情问题→真实 API）。

**理由**：
- 「店长助手」有真实用户和画面感，比「通用助手」好讲、好演示
- `SqliteTool` 让「多工具 Agent」名副其实（之前只有一个真数据工具，名不副实）
- Text2SQL（NL→SQL + 安全校验 + 错误重试）本身是高价值面试点，复活后与 REPLAN 形成呼应

**暴露的问题（有价值的排障）**：加第二个工具后，`ClarificationChecker`（原为疫情数据源设计的）误把 sqlite 工具调用判成"信息不足"。根因是**单一数据源时代的检查器遇到多工具时代的水土不服**。修复：澄清追问只针对"数据源类动作"（global/country/history），非数据源工具（sqlite/answer）直接放行。

**关联**：依赖 ADR-014（工具抽象）+ ADR-010（数据源抽象）。旧 `planner.py` 及医院演示数据（departments/patients）成为待清理死代码。

## ADR-018：接入天气数据源，实现「天气 × 销量」多工具协同备货建议

**背景**：咖啡店经营助手需要「结合天气预报 + 历史销量辅助分析备货」这个核心场景。单一数据源（本地库或天气）都给不出跨数据源的分析依据。

**决策**：
1. **新增 `OpenMeteoSource`**（第二个真实数据源）：免费、无需 key、同时支持「未来预报」和「历史天气」。
2. **天气码映射**：内置 WMO weather code → 中文（晴/多云/阴/小雨/中雨/大雨/阵雨…），让 API 数字码可读化。
3. **复用 `DataSourceTool` 包装**：天气数据源直接 `DataSourceTool(OpenMeteoSource())`，不单独写 WeatherTool（依赖倒置的价值——包装逻辑通用）。
4. **多工具协同**：planner 规划出「查天气 + 查历史销量」两步，executor 依次执行，answer 汇总成备货建议。

**理由**：天气是咖啡店销量的核心外部变量；「未来预报 + 历史规律」拼起来，才能产出「雨天少备冰饮、多备热饮」这种单工具给不出的经营洞察。

**暴露的两个真实问题（有价值的排障）**：
1. **数据字典不一致**：本地库 `weather` 字段存「晴/阴/雨」，但 LLM 生成 SQL 时用了「下雨天」，导致匹配不上、查空。修复：在 schema 提示词里**显式声明 weather 字段的合法取值**。
2. **工具参数格式写死**：`DataSourceTool.parameters()` 原来写死了疫情格式（`country:USA`），对天气数据源不适用。修复：给 `DataSource` 加 `action_examples()` 方法，让**每个数据源自述自己的 action 格式**（开闭原则）。

**关联**：依赖 ADR-017（咖啡店助手定位）+ ADR-010（数据源抽象）+ ADR-014（工具抽象）。

## ADR-019：正式链路接通 + 意图路由适配「经营场景」

**背景**：核心功能（天气 × 销量备货建议）在命令行冒烟测试里已跑通，但 `chat.py` 正式链路和前端界面仍停留在「疫情助手」时期，用户在网页上问不出咖啡店经营问题。

**决策**：
1. **`chat.py` 注册四工具**：`SqliteTool`（经营库）+ `DataSourceTool(OpenMeteoSource)`（天气）+ `DataSourceTool(DiseaseShSource)`（疫情，保留作多源证据）+ `AnswerTool`。
2. **意图路由适配**：`IntentClassifier` 的提示词从「疫情示例」改为「咖啡店经营示例」，否则「下周备货」这类问题会被误判为 chat、绕过状态机（**真实排障**）。
3. **前端人设改造**：标题、欢迎语、示例卡片、能力披露、数据来源标注全部改为「咖啡店店长」场景。
4. **疫情数据源保留但不主推**：作为「多数据源热插拔」的架构证据（加一个数据源只需写类 + 注册一行）。

**理由**：意图分类器是「单一数据源时代」的产物，其示例词库隐含「疫情」假设；换赛道后必须同步适配，否则路由与产品定位脱节。

**关联**：依赖 ADR-009（意图路由）+ ADR-018（天气工具）+ ADR-017（咖啡店定位）。

## ADR-020：澄清追问通用化（规则层管确定性缺口，语义层管所有工具）

**背景**：原 `ClarificationChecker` 只对「疫情数据源动作」做澄清（查国家缺国家名才反问），咖啡店问题（sqlite 工具）指代不清时只能靠 Text2SQL 失败重试兜底，没有「主动反问」。阶段三补齐这个体验缺口。

**决策**：分层策略——
1. **规则层**：仍只对数据源动作（global/country/history）做「必填参数」硬检查（确定性、免费、可测试）。
2. **大模型语义层**：改为对「所有查询类工具」（含 sqlite）做「语义歧义」检查，识别「那个/它」指代不清。
3. **`_has_query_action` 短路**：纯 answer 工具（无查询动作）不参与澄清。
4. **防过度澄清**：提示词明确「这个月/最近/今天」等相对时间是明确的，不强制追问细分维度。

**理由**：呼应「确定性逻辑与 LLM 分离」原则——能确定的事（缺参数）交给规则，不确定的事（指代歧义）交给 LLM；且咖啡店的歧义多为「指代不清」，只能靠 LLM 语义理解，规则做不了。

**暴露的真实问题**：初版让 sqlite 也走语义层后，LLM 对「这个月」过度较真，把明确的相对时间误判为信息不足。修复：提示词显式声明「相对时间不算信息不足」，抑制过度澄清。

**关联**：依赖 ADR-017（咖啡店定位）+ 阶段二澄清机制。旧 `planner.py`、医院演示数据（patient/repository）在本阶段一并清理为死代码。

## 架构分层总览

```
┌─────────────────────────────────────┐
│        前端 (React + Vite)          │  ← 对话界面、流式展示、图表
├─────────────────────────────────────┤
│  认证层 (JWT + 资源隔离 owner校验)  │  ← ADR-011：登录/身份/越权防护
├─────────────────────────────────────┤
│      API 层 (FastAPI 路由)          │  ← 聊天接口、数据源接口、SSE
├─────────────────────────────────────┤
│     Agent 引擎 (LangGraph)          │  ← 状态机：规划/执行/反思/决策
├─────────────────────────────────────┤
│  意图路由 (IntentClassifier)        │  ← 闲聊/分析 分流（ADR-009）
├─────────────────────────────────────┤
│  Text2SQL 引擎 (sqlglot + LLM)      │  ← NL→SQL→校验→执行
│  数据源层 (DataSource + Registry)   │  ← 多源热插拔（ADR-010）
├─────────────────────────────────────┤
│   LLM Provider (LangChain 抽象)     │  ← DeepSeek / GLM 可切换
├─────────────────────────────────────┤
│   数据层 (SQLAlchemy + SQLite)      │  ← 业务表 + 用户表 + 会话表
└─────────────────────────────────────┘
```
